# Spec 0007: Asks, the operator's decision queue

Status: draft. Extends spec 0005 (the console and the tool registry)
and spec 0001's operator relationship. An ASK is the agent's formal
request for operator attention: a decision it may not make alone, a
question only the operator can answer, or a task only the operator can
perform.

## 1. The problem

Today an ask exists only as a block in the agent's own `ASKS.md`, in
its state repo. Nothing surfaces it, nothing tracks whether it was
answered, and the answer, when it comes, arrives as prose in a channel
message that the ask itself never records. The agent's summary is the
only delivery mechanism, and a wake that dies before sending its
summary loses the ask entirely (this has happened).

Meanwhile the agent already files its work in the right public places:
GitHub issues, PRs, emails. Those stay. What is missing is the
operator's queue: the small set of things WAITING ON A HUMAN, each
with its state, its decision, and the conversation that resolved it.

## 2. The object

An ASK is durable, threaded, and decidable:

- `id`, `agentId`, `createdAt`, `title` (one line), `body` (the ask in
  full), optional `links` (the GitHub issue, PR, or URL it belongs to),
  and `kind`.
- `kind` is the agent's declaration of what it needs: `decision` (a
  yes or no), `request` (an action only the operator can take), or
  `question` (an answer). Kind is a HINT for the surface, never a
  restriction: every operator action is available on every ask,
  because the agent's framing is sometimes wrong and the operator is
  the authority on what an ask actually is.
- `state` ∈ `open`, `acknowledged`, `allowed`, `declined`, `closed`.
  The operator moves an ask to acknowledged ("on it"), allowed, or
  declined; either party closes it when it is done. Closed is
  terminal; everything else can still move.
- `thread`: an append-only list of entries, each `{at, author, kind,
  state?, text?}` where author is `agent` or `operator` and kind is
  `message` or `state_change`. A `state_change` entry ALWAYS carries
  `state` (the state it moved the ask to) and MAY carry `text`; a
  `message` entry always carries `text` and never `state`. So a
  wordless decision is still fully readable from the thread alone,
  and an explained one lands its reason in the same act that makes
  it, where the reason will be looked for later.

## 3. Its own Gatekeeper

Asks get their OWN Gatekeeper (`asks`), because that is how every door
in this chassis is built: one capability, one Worker, one credential
boundary, one ledger. The agent reaches it only through the porch with
its per-agent bearer; the operator reaches it only through the
binding-only `Ops` entrypoint; every state change is a row in the
Gatekeeper's own Ledger, mirrored to the chronicle like every other
Gatekeeper's. Folding asks into an existing Worker would save a
deployment and cost the property that makes this chassis legible: that
a door's blast radius is the door.

State lives in one `AskBox` Durable Object per colony, which makes
transitions ATOMIC by construction rather than by query cleverness:
the DO serializes, so a state change and its thread entry commit in
one turn, and no interleaving can produce a decision without its
record (spec 0002's transactional-event lesson, applied from the
start).

**Concurrent transitions are compare-and-set, and losing is a
first-class answer.** Every state change names the state the caller
believed the ask was in, and the DO commits only if it still holds.
If it does not, NOTHING is written and the call answers `409
ask_state_moved` with the ask's current state and its thread tail, so
the caller sees what happened instead of overwriting it: an operator
who declines an ask the agent closed a second earlier gets told so,
and decides again with the truth. `closed` is terminal, so a
transition out of it always loses. Thread messages carry no expected
state and are always allowed (including on a closed ask, where they
are the record of an afterthought); they never change state.

The Gatekeeper holds no credential of its own: asks are data, not an
outward capability. Its bounds are therefore the ordinary ones (the
per-agent bearer, the roster, and size caps on title, body, and
message text) rather than a spend or send limit.

## 4. The agent's door

`operon ask` (porch, per spec 0001):

- `operon ask "<title>" --body <b> [--kind decision|request|question]
  [--link <url>]` opens an ask and NOTIFIES the operator, because an
  ask that nobody sees is the failure this spec exists to end.
- `operon ask list` the agent's own asks with state and unread
  operator activity.
- `operon ask reply <id> --text <t>` adds to the thread (the agent
  answering a question the operator asked back, or reporting that the
  ask is now moot).
- `operon ask close <id> [--text <t>]` when the agent no longer needs
  it. The agent's door reads the ask's current state and passes it as
  the expected state, so a close that races an operator decision loses
  cleanly and the agent is told the new state rather than erasing it.

Filing elsewhere is unchanged: an ask that belongs in a GitHub issue
still becomes one, and the ask record LINKS it rather than replacing
it. The rule is: if it needs the operator's attention, it also becomes
an ask.

## 5. The operator's surface

Registry tools (spec 0005 parity: the console, the REST API, and MCP
get these identically):

- `ask_list` (read) with state filter; `ask_read` for one ask with its
  full thread.
- `ask_decide` (decision, ledgered): `{askId, expectedState, decision:
  acknowledged | allowed | declined, text?}`, compare-and-set per §3.
  The console passes the state it rendered, so a stale tab cannot
  silently overwrite a newer decision.
- `ask_reply` (decision, ledgered): a thread message with no state
  change.
- `ask_close` (decision, ledgered): `{askId, expectedState, text?}`,
  compare-and-set per §3.

The console gains an ASKS section: open asks first, each with its
kind, age, agent, links, full body, and thread. The suggested action
for the ask's kind is offered prominently and the others remain
available. Agent-authored text renders under the spec 0005 §8 rules
(text nodes only, links dead by default, provenance marked): an ask is
untrusted mind output, and it is asking for a decision, which makes it
the highest-value place in the system for an injected instruction to
be read as the operator's own idea.

## 6. Delivery back to the agent

An answer nobody reads is not an answer. Operator activity on an ask
reaches the agent through the SAME path as mail and channel messages:
the wake-start pull, and `operon pull` mid-wake. An ask with unread
operator activity is delivered as a counted, pointed line (the ask id
and title, never a bulk dump), and reading it acks it. A decision the
agent has not yet seen is therefore never lost to a dead wake, because
the record, not the message, is the truth.

## 7. Audit and notification

Every state change writes a ledger row through the ops gateway's
existing decision doctrine (intent first, refuse on audit failure).
Ask creation notifies the operator; operator activity does not notify
the agent (agents do not receive pushes, they pull). The notification
carries the ask id and title only: the body is untrusted text and
belongs where it can be rendered safely.

## 8. Out of scope

- Assigning asks to anyone but the operator (there is one operator).
- Due dates, priorities, or escalation. An ask is either open or not;
  a colony small enough for one operator does not need a workflow
  engine.
- Migrating historical `ASKS.md` content. The file stays the mind's
  own notes; new asks are records.
